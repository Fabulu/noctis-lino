      ( *** geoconv - float to int at the LIVE top of the x87 stack ***

	This is a LIBRARY.  It needs fpabi, fpctl, fpx87 and fpconv, which
	the top-level programme lists BEFORE it.  It modifies none of them,
	so FLOATPOLICY.md's contract and tests/test_floatcontract.py stay
	literally true: everything new lives in this wave's own namespace.

	----------------------------------------------------------------
	WHAT IS MISSING FROM fpconv, AND WHY IT MATTERS
	----------------------------------------------------------------

	FLOATPOLICY.md 3.3 and 6.1:

	    "The engine has no way to truncate an unstored extended value.
	     FToIntChop begins `fld qword [FA0]`, so the 80-bit intermediate
	     is narrowed to binary64 BEFORE the truncation. ... On hardware
	     the two differ."

	Wave 4 closed that for exactly ONE site - nsident.txt's
	NsIdentChop16, the srand at NOCTIS-0.CPP:3970 - by open-coding the
	whole expression as one fragment ending in fldcw/fistp/fldcw.  It
	could not be generalised because a value that is still in st(0)
	cannot be handed between two L.in.oleum routines: there is no
	calling convention that carries the x87 stack.

	So a general FToIntChopExt cannot exist as "chop whatever is on the
	stack".  What CAN exist, and is what this file provides, is one
	fragment per EXPRESSION SHAPE, each of which builds its value and
	chops it without ever storing it.  The shapes here are not invented:
	they are the shapes of the ten float-argument call sites in
	prepare_nearstar that can actually differ (site registry, nstopo.txt).

	    :4090 :4091 :4196 :4197   random/zrandom (10 * <double>)
	    :4195                     zrandom (300 * <double>)
	    :4092 :4198               random (<double> + 10*fabs(<double>))
	    :4093 :4199 :4094         random (<double>)          - see below
	    :4089                     random (300 * <float>)     - see below

	:4093, :4199 and :4094 pass a bare double array element.  Loading a
	binary64 into an 80-bit register is exact, so live and spilled chop
	are the SAME operation there and no fragment is needed.  :4089
	multiplies 300 by the `float` nearstar_ray; 300 * (24-bit
	significand) needs at most 33 bits, so that product is exact in both
	precisions too.  Seven sites can differ, three cannot.  That is a
	property of the operands and it is asserted, not assumed: geocast's
	battery 4 runs the exact-by-construction shapes and REQUIRES zero
	disagreements, so if the reasoning is wrong the probe says so.

	----------------------------------------------------------------
	WHICH ONE IS THE ORIGINAL'S
	----------------------------------------------------------------

	LIVE.  Not by argument from Borland's calling convention - read out
	of the shipped NOCTIS.EXE.  __ftol is at 0000:1265 and its whole
	body is:

	    1265  push bp / mov bp,sp / sub sp,0Ah
	    126C  fnstcw word [bp-2]
	    1271  mov  al, [bp-1]          ; save the high byte
	    1274  or   byte [bp-1], 0Ch    ; RC <- 11, chop.  OR, not AND/OR.
	    1279  fldcw word [bp-2]
	    127D  fistp qword [bp-0Ah]     ; truncates whatever is in st(0)
	    1280  mov  [bp-1], al          ; put the saved byte back
	    1284  fldcw word [bp-2]
	    1287  mov ax,[bp-0Ah] / mov dx,[bp-8]   ; low 32 bits, in DX:AX
	    1290  retf

	It takes no parameter.  Its input is st(0), so the value it chops is
	whatever the caller left on the stack, at whatever precision the
	caller left it.  And the call sites leave it live: at :4089 in
	prepare_nearstar (file offset 61546 in NOCTIS.EXE),

	    8D7A  fld   dword [0x108C]     ; 300.0f
	    8D7F  fmul  dword [0x027F]     ; * nearstar_ray
	    8D83  lcall 0,0x1265           ; __ftol   <- no store in between
	    8D88  push  ax                 ; random(int)

	and the same shape at :4090 (8CB2 fld qword p_orb_seed / 8CB7 fmul
	dword 10.0f / 8CBB lcall __ftol), :4092 (8D24 fadd qword p_orb_seed
	/ 8D28 lcall), :4093, :4094, :4198 and :4199.  Not one of the eleven
	sites has an fstp between the last arithmetic instruction and the
	call.  The LIVE reading is the original's, at every one of them.

	Two consequences that are easy to get wrong and are reproduced here:

	  * __ftol ORs 0Ch into the high byte.  It does not clear RC first.
	    Under the game's 133Fh the two are the same; under a hypothetical
	    RC=10 they are not, and a port that "tidies" this into
	    AND 0F3FFh / OR 0C00h has changed the instruction.

	  * it is `fistp QWORD`, and only the low 32 bits are returned.  A
	    32-bit fistp is a different operation: masked, it stores the
	    integer indefinite 80000000h for every out-of-range value
	    instead of letting the low half through.  geocast battery 8
	    measures that difference rather than asserting it.

	Both fragments below reproduce the RC flip; they differ ONLY in
	whether an fstp qword / fld qword pair sits in front of it.

	The Spill variants exist so the two can be MEASURED against each
	other rather than argued about.  They are also exactly what a port
	built on fpconv alone is forced to produce, so the gap between the
	two pairs is the size of the mistake that was available.

	----------------------------------------------------------------
	INTERFACE
	----------------------------------------------------------------

	Every routine here:
	  pre   caller is inside FEnter with [FCW] = 133Fh
	  post  FI = the 32-bit chopped value; x87 stack balanced; the
		control word is exactly what it was on entry

	  GeoSetK      in A = 0 for 10.0, 1 for 300.0, 2 for 100.0
		       sets the gcK pair used by the Kmul routines

	  GeoKMulChopLive    FI <- (long) live ( K * FB )
	  GeoKMulChopSpill   FI <- (long) fl64 ( K * FB )
	  GeoSeedTiltChopLive   FI <- (long) live ( FB + 10*|FC| )
	  GeoSeedTiltChopSpill  FI <- (long) fl64 ( FB + 10*|FC| )
	  GeoPlainChop          FI <- (long) FB          both readings agree
	  GeoQuoMulChopLive     FI <- (long) live ( FB / FC * FC )
	  GeoQuoMulChopSpill1   FI <- (long) live ( fl64(FB/FC) * FC )
	  GeoQuoMulChopSpill2   FI <- (long) fl64 ( FB/FC * FC )
	  GeoChop16            FI <- low 16 bits of FI, SIGN extended.
		       random() takes an `int`, and Borland large-model
		       int is 16 bits.  srand()'s is zero extended - that
		       asymmetry is nsident.txt's, not this file's.

	  GeoSeedStore100      FA <- FC*FB + FI/100, one live expression
	  GeoRatioStore50      FA <- FI/50, one live expression
	  GeoRatioStore500     FA <- FI/500, one live expression
	  GeoRatioStore5000    FA <- FI/5000, one live expression
	  GeoEccStore2000      FA <- 1 - FI/2000, one live expression
	  GeoPlanetRayStore    FA <- FI*0.001 + 0.01, one live expression
	  GeoMoonRayStore      FA <- FI*0.05 + 0.1, one live expression

	The Store routines reproduce the x87 statement boundary as well as
	the live argument boundary: their only narrowing store is the final
	assignment to binary64 FA.                                             )

      ( GeoChopEnter - read the ambient word, build the chop word.
	Every routine below opens with this and closes by loading gcsav
	back, which is __ftol's own bracket and NOT FEnter's. )

"GeoChopEnter"
	[gcsav] = 0;
	=> FCWRead; A = [FI]; [gcsav] = A;
	A = [gcsav]; A | 0C00h; [gcchop] = A;
	end;

      ( GeoChop16 - Borland large-model `int` is 16 bits, and random()'s
	parameter is an int.  The 32-bit fistp runs first and the low 16
	bits are then SIGN extended, because that is what the original's
	register usage does.  fistp m16int would be wrong: masked, it
	stores 8000h for every overflow, and the overflow is the normal
	path - classes 1, 3, 4 and 9 exceed int16 at their outer planets
	by up to 6.7x (FLOATSITES.md 4.2). )

"GeoChop16"
	A = [FI]; A & 0FFFFh; [FI] = A;
      ? [FI] '< 8000h -> gc16done;
	A = [FI]; A - 65536; [FI] = A;
    "gc16done"
	end;

      ( FC*FB + FI/100.  FC is the integer coefficient already converted
	to an exact double; FB is the stored star/parent ray; FI is the
	random result.  Used by :4089 and :4195. )

"GeoSeedStore100"
	{
	    DD 87 <dFC0 mtp bytesperunit>	(fld   qword [edi+FC0*4])
	    DC 8F <dFB0 mtp bytesperunit>	(fmul  qword [edi+FB0*4])
	    DB 87 <dFI mtp bytesperunit>	(fild  dword [edi+FI*4])
	    DC B7 <dgcHun0 mtp bytesperunit>	(fdiv  qword [edi+gcHun0*4])
	    DE C1				(faddp st1,st0)
	    DD 9F <dFA0 mtp bytesperunit>	(fstp  qword [edi+FA0*4])
	}
	end;
