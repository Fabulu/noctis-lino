	top-level programme lists before it.

	Subject: NOCTIS-0.CPP:4047-4057 (starnop) and :4059-4376
	(prepare_nearstar).  Transcribed from niv-plus/source/NOCTIS-0.CPP,
	expression for expression, with the line numbers of that file.

	----------------------------------------------------------------
	WHAT IS IN AND WHAT IS OUT
	----------------------------------------------------------------

	IN:   nearstar class, seed and binary32 stellar radius.

	OUT:  nop, nob, every body's p_type/p_owner/p_moonid, phase-A
	      p_orb_seed/p_tilt/p_orb_tilt/p_orb_ecc/initial p_ray, exact
	      radian and integer-degree orientation, and phase-F final
	      p_ray/p_orb_ray.

	That line is not a convenience.  Every draw in prepare_nearstar
	whose value selects a branch, a count or a type takes an INTEGER
	argument - all of :4082, :4096, :4098, :4103, :4112-4114, :4123,
	:4127, :4134, :4138, :4148, :4152, :4153, :4161, :4183, :4186,
	:4201, :4213, :4214, :4238, :4255, :4348, :4354, :4358.  The
	eleven float-argument sites feed the retained landing/orbit geometry.
	Since rand has
	exactly ONE caller in NOCTIS.EXE - random() is a real out-of-line
	function, not a macro, and the call to rand is not predicated -
	one rand() is consumed per random() for every n.  Phase F already
	used real NsZRandom calls; their returned values now also feed the
	source radius formulas without changing that RNG stream.

	----------------------------------------------------------------
	THE SITE REGISTRY - exactly ELEVEN live geometry sites
	----------------------------------------------------------------

	Each row is ONE call site in the code below, marked "LIVE SITE nn".
	A site that draws twice is a real NsZRandom.  The live x87 cast and
	assignment boundaries preserve the original RNG schedule and geometry.

	 nn  line   draws  expression
	 --  -----  -----  --------------------------------------------
	  1  :4089    1    random (300 * nearstar_ray)
	  2  :4090    2    zrandom (10 * nearstar_p_orb_seed[n])
	  3  :4091    2    zrandom (10 * nearstar_p_orb_seed[n])
	  4  :4092    1    random (p_orb_seed[n] + 10*fabs(p_orb_tilt[n]))
	  5  :4093    1    random (nearstar_p_orb_seed[n])
	  6  :4094    2    zrandom (nearstar_p_ray[n])
	  7  :4195    2    zrandom (300 * nearstar_p_ray[n])
	  8  :4196    2    zrandom (10 * nearstar_p_orb_seed[q])
	  9  :4197    2    zrandom (10 * nearstar_p_orb_seed[q])
	 10  :4198    1    random (p_orb_seed[q] + 10*fabs(p_orb_tilt[q]))
	 11  :4199    1    random (nearstar_p_orb_seed[n])   PARENT index
	 --  -----  -----
	 11 sites, 17 draws

	:4094 also contains `random (1000)`, whose argument is an integer
	literal, so it is a plain NsRandom with the value discarded and it
	is NOT one of the eleven.  The two operands of the `*` at :4094 are
	unsequenced in C; the order changes which draw lands where but not
	how many are taken, so the topology is unaffected either way.  The
	order here is left to right, matching the plan's control.

	----------------------------------------------------------------
	TWO BEHAVIOURS A TIDY PORT SILENTLY REPAIRS.  Both are required.
	----------------------------------------------------------------

	1. :4213 `if (n > 7 && random(c)) r = 7;` fires on the FIRST moon
	   too, where c == 0.  random(0) still calls rand().  Skipping it
	   because "the answer is always 0" desynchronises the stream.

	2. :4232 `if (n > 7) r = 7;` runs BEFORE the :4238 test, and that
	   test can then set r = 5, overwriting the 7.  Reaching :4238 at
	   all requires s == 6 exactly: r can only be 3 from :4201, :4221
	   rewrites r=1 unless s==6 or s>=9, and :4235 additionally
	   demands s < 9.

	And one that is NOT repaired here: nearstar_p_moonid[q] is written
	only inside the moon loop, so a PLANET's slot keeps whatever the
	previous star left in it.  That is real behaviour, it is invisible
	(DL prints owner.moonid only for moons), and a port that helpfully
	zeroes or computes it is inventing state.  This file does not touch
	p_moonid for planets; the interchange record writes 0 there and the
	field must never be graded for k < nop.

	----------------------------------------------------------------
	INTERFACE
	----------------------------------------------------------------

	    NsStarnop   in  [nsclass], [nsseedin]
			out [nsnopest]
			Does its OWN srand and consumes 3 draws.  Run it
			BEFORE NsPrepare and call NsResetAll in between,
			or its draws pollute prepare_nearstar's counts.

			starnop's seed expression at :4051 is textually
			identical to prepare_nearstar's at :4080, so it
			takes the already-derived [nsseedin] rather than
			recomputing it.  That also keeps the two coherent

	    NsPrepare   in  [nsclass], [nsseedin] = srand argument
			out [nsnop] [nsnob], nsptype/nspowner/nspmoonid
			    and nsrng's counters                        )

      ( int starnop (double star_x, double star_y, double star_z)
	{
		int r;
		srand ((long)x%10000*(long)y%10000*(long)z%10000);
		r  = random (class_planets[ap_target_class] + 1);
		r += random (2);
		r -= random (2);
		if (r < 0) r = 0;
		return (r);
	}

	Note it indexes class_planets with ap_target_class, not with
	nearstar_class.  In this port the caller supplies the class it
	means, in [nsclass]. )

"NsStarnop"
	A = [nsseedin];
	=> NsSrand;
	E = nsclasstab; E + [nsclass]; A = [E]; A + 1;
	=> NsRandom;
	[nsnopest] = A;
	A = 2; => NsRandom;
	B = A; A = [nsnopest]; A + B; [nsnopest] = A;
	A = 2; => NsRandom;
	B = A; A = [nsnopest]; A - B; [nsnopest] = A;
      ? [nsnopest] >= 0 -> nssnok;
	[nsnopest] = 0;
    "nssnok"
	end;
